# Background tool use proof of concept

Stage 5 experiment for ticket `e71014c`, based on the
[Cog tool-use lifecycle](../../docs/tool-use-lifecycle.svg).

- Advertise two static function templates through the OpenRouter Chat Completions
  API. The model selects `start_background` or `background_status` with
  `tool_choice: auto`. Dispatch validates arguments against the same template
  used to generate each declaration. The next request includes the assistant
  call and the tool result with the matching call ID.
- Return a launch receipt as the terminal result of the start call. Keep its
  job running independently while the same dispatcher accepts further prompts.
  A status call observes the job's outcome under its own provider call ID.
- Retain the PID for diagnostics and the Linux pidfd as the live process
  reference. Register the pidfd with the event loop for exit readiness.
  Cancel through the pidfd, reap the owned child, and close the fd. The model
  sees an opaque job ID that remains usable after reaping.

## Run

Use Linux with pidfd support and a Python build exposing `os.pidfd_open`,
`os.P_PIDFD`, and `signal.pidfd_send_signal`. Run from the checkout root.
The system Python 3.13 worked on the verification machine.

```sh
/usr/bin/python3 -B pocs/tool-use/test_proof.py -v
/usr/bin/python3 -B pocs/tool-use/proof.py --live
```

The offline tests use a scripted provider and real child processes. The live run
reads `OPENROUTER_API_KEY` or pi's existing OpenRouter credential and makes
seven generation requests with a maximum of 256 output tokens each. Use
`--model` to explicitly select another tool-capable OpenRouter model.
Each run sends synthetic prompts and results. The worker runs a fixed program
with an empty environment. The driver holds a pipe open to keep the worker
alive across the two intervening prompts, then closes the pipe to let it finish
and generate a fresh result.

## Evidence

The November 19, 2026 run requested `deepseek/deepseek-v4-flash` on OpenRouter
and completed all seven requests across four prompts in the same history.

| Prompt | Observed result |
| --- | --- |
| Start the job labeled `proof` | The model chose the launch template with the correct argument and repeated the returned job ID. |
| Ask an unrelated arithmetic question | The model replied `42` without a tool call. A non-consuming `waitid(P_PIDFD, ... WNOWAIT)` probe confirmed the same child was still alive after the reply. |
| Inspect the job | The model chose the status template, used the earlier job ID and reported `running`. The child was still alive. |
| Inspect the job after release | The event loop observed exit and reaped the child with code 0. The model used the same job ID and reproduced the random result generated by the child. |

The offline suite verifies correlation, rejection of invalid arguments before
launch, cancellation of two distinct live children, and reaping even if a
cleanup waiter is cancelled. A second kernel wait on a duplicated pidfd returns
`ECHILD` after the owning wait has reaped the child.

## Scope

This standalone Python PoC exercises Chat Completions templates, one live
dispatcher, and direct children. Cog's existing workspace process helper uses
a subreaper and process group for descendant ownership. Production work still
needs to give the long-running job its own owner, admission and durability
contract, including reconciliation when the dispatcher restarts. These
experiments use the provider's function schema and tool-call IDs directly.
[OpenRouter Chat Completions API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request)
